Architecture

Telegram calls a webhook on API Gateway. API Gateway starts a Step Functions execution directly, with no Lambda in between. The workflow owns all the logic and all the waiting. Lambda functions exist only where there is no native integration: understanding a message, changing inventory, and talking to Telegram.

API Gateway (REST)Receives the webhook and starts the workflowDirect service integration: Telegram gets its 200 at once, and no code runs for the handoff

A message, step by step

What happens when someone sends «Guardé caldo de pollo en el refri»:

  1. Telegram posts the update to /prod/webhook/<secret>. Only Telegram knows the secret path segment.
  2. API Gateway calls StartExecution with the update as input and names the execution tg-<update_id>. If Telegram redelivers the same update, the name already exists and no second execution starts. API Gateway always answers 200.
  3. The Route state looks at the update: a button press goes to ResolveButton, a message goes to Understand.
  4. understand handles slash commands itself and sends free text or a photo to Bedrock. It returns {intent, food, category}, already validated.
  5. ByIntent branches: store, eaten or thrown away, list, invite, link, or a plain reply (help, unknown, voice not supported).
  6. For a store, inventory looks up the shelf life, writes the item and returns its two timestamps: when to remind and when it expires.
  7. notify sends the confirmation as text and as a voice note. The execution then stays alive, waiting.

Life of a stored item

Each stored item keeps one execution paused until its deadline. After every wait the workflow re-reads the item from DynamoDB, so something already eaten triggers nothing. Reminders and questions go to whoever stored the item. Nothing leaves the fridge by silence: an unanswered item stays on the list, flagged for review.

Item stateSet when
ACTIVEThe item is in the fridge and nobody has resolved it
ACTIVE + needs_reviewA question went unanswered. The item stays on the list under “Vencidos, por revisar”
CONSUMEDSomeone says it was eaten, by button or by text
DISCARDEDSomeone says it was thrown away, by button or by text

Human in the loop

The question at the deadline is a real pause, not a poll. The AskWhatHappened state uses lambda:invoke.waitForTaskToken: the execution stops and hands out a token that only a button press can redeem.

  1. notify saves the task token on the item before it sends the buttons, so a fast tap can never arrive ahead of the token it needs.
  2. The user taps a button. Telegram sends a new update, which starts a second, short execution.
  3. That execution calls inventory to apply the button with a conditional write. The call returns the saved token and removes it from the item.
  4. The short execution calls SendTaskSuccess with the token. The paused execution wakes up with the answer.
  5. If nobody answers within the timeout, the pause ends with States.Timeout and the workflow moves to Escalate.

One question at a time

Several items often expire together, and a burst of questions gets lost in the chat. So each person has one question turn. It is a slot on that person's profile, taken with a conditional write before the question is sent.

  • Turn taken: the question goes out and says how many more items are waiting.
  • Turn busy: the execution saves a wake-up token on its item and pauses in WaitTurn.
  • Turn freed: an answer or a timeout releases the slot and wakes the item that expired first, with SendTaskSuccess.
  • Fallback: a waiting execution also retries on its own every 15 minutes (every 5 seconds in demo mode), and a turn nobody released expires by itself. A failed execution can never block the questions behind it.

Rules built on top of the pause

  • “Sigue ahí” postpones the question one day, twice at most. The workflow counts the questions in a variable and flags the third as last_chance.
  • The last call has two buttons only: “Ya me lo comí” and “Ya lo tiré”. The goal is to always learn how the food ended up.
  • Eating food after saying it was still there past its deadline, or after it was left for review, gets a health message. Answering the reminder or the first deadline question counts as on time, because a button can't tell when the food was eaten. The reply, sent as text and voice, says that throwing food away is hard and that this is about health.
  • An unanswered item is escalated, not removed. It stays in the fridge flagged for review, and every other member of the fridge gets a message. With nobody else in the fridge, the bot explains what /familiar is for and invites the user to share it.
  • Flagged items are reviewed one by one. The list offers a “Revisar vencidos” button. Each answer brings the next flagged item, asked in neutral words because a relative may be the one answering.
  • A second tap is harmless. The conditional write fails and the bot answers that the item was already resolved.

Two modules have no handler of their own. messages.py holds every user-facing sentence in Spanish, so wording changes never touch logic. telegram.py is a small Bot API client on the standard library, which keeps the deployment package free of third-party dependencies.

Data model

A fridge is one partition of the items table. The partition key is the chat id of whoever started the fridge, and item_id is the sort key. Each person's profile says which fridge they belong to: their own by default, or the one they joined through an invitation.

RecordKeyMain attributes
Stored item<fridge> / T#<random id>food, category, status, stored_by, expires_epoch, needs_review, task_token while a question is open, turn_token while waiting for the turn
Profile<chat> / PROFILEfirst_name, fridge_id, and the question turn: asking, asking_until
Fridge<fridge> / FRIDGEmembers, the set of chats that share it
InvitationINVITE / <one-time code>fridge_id, inviter_name, ttl (7 days, removed by DynamoDB TTL)

Every member sees the same list and can resolve any item. Any member can invite. Joining another fridge leaves the previous one.

The shelf-life table maps 29 food categories to a conservative number of days. Examples: raw poultry, raw fish and guacamole 1 day; most cooked dishes 3; fresh cheese 5; hard-boiled eggs 7; hard cheese 21. A food outside the list gets 2 days, and the bot says it used a short default.

What the model does, and what it does not

Bedrock only extracts. It receives the text or the photo and returns one JSON object with an intent, a short food name and a category. It never decides how long food is safe.

  • The category must be one of the 29 keys. Anything else becomes other.
  • An unknown intent, malformed JSON or a store without a food name becomes unknown, and the bot asks again.
  • The system prompt treats the user message as data and tells the model never to follow instructions inside it.
  • Text is cut at 500 characters, the food name at 60, and temperature is 0.
  • Photos go from Telegram straight to Bedrock in memory. They are never stored.

Security

  • Webhook: Telegram cannot sign requests, so the control is an unguessable path segment plus throttling at 10 requests per second (burst 20).
  • Bot token: an SSM SecureString, read once per execution environment. Error messages report the API method and Telegram's description, never the URL that embeds the token. A test pins this.
  • Least privilege: each function has its own role. The API Gateway role can only start this state machine.
  • Button data is untrusted: it is parsed, length-checked and applied only to items in the fridge the sender belongs to.
  • Invitations: the only way into a fridge. Each is a random code that works once and expires in 7 days, so a guessed chat id cannot join a stranger's fridge.
  • Data at rest: the items table is encrypted and uses on-demand capacity.

Deploy and operate

There is no pipeline. One script packages the code, deploys the stack, seeds the shelf-life table and registers the webhook. It needs only the AWS CLI and Python 3.

./scripts/store_bot_token.sh        # once: saves the token in SSM
./scripts/deploy.sh                 # real timings

# demo: a day lasts 20 seconds, questions time out after 45
SECONDS_PER_DAY=20 ASK_TIMEOUT_SECONDS=45 ./scripts/deploy.sh

Before creating anything, deploy.sh checks that the token exists, that the Bedrock model answers in the chosen region and that Telegram accepts the token.

Current deployment: region us-east-2, demo timings. The account's organization policy denies most services in us-east-1, so export AWS_REGION=us-east-2 AWS_DEFAULT_REGION=us-east-2 in the same shell before running any script.

Limits

  • Shelf-life values are conservative lower bounds of general USDA and FoodKeeper guidance. The bot is a reminder aid, not food-safety advice.
  • Voice messages from the user are not understood yet. The bot says so and asks for text or a photo.
  • A person belongs to one fridge at a time. Joining another one is refused while it would leave food in a fridge nobody else shares.
  • Questions asked from the review button do not take the question turn, so one can overlap with a scheduled question.
  • Planned next: send a shopping list and have every product stored with a recommended expiry date from a third-party source.
  • A change to the webhook method needs a new API Gateway deployment: rename WebhookDeploymentV1 in the template.
  • Telegram is the prototype channel. WhatsApp and voice input are the natural next steps.
